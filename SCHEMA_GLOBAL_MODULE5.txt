╔════════════════════════════════════════════════════════════════════════════════════════════════════╗
║                                    GESTION DE LA CAPACITÉ                                         ║
╚════════════════════════════════════════════════════════════════════════════════════════════════════╝

    Événement: Capacité 50 places
    ├─ 2 billets confirmés (valid)
    ├─ Places restantes: 48
    │
    └─ Si nouvel inscrit:
       ├─ Capacité > 0 ? → Créer ticket, status='valid'
       └─ Capacité = 0 + waitlist ? 
          ├─ OUI → Ajouter à event_waitlist
          │        ├─ Position déterminée (MAX+1)
          │        ├─ Email: "Vous êtes en position #X"
          │        └─ Attendre promotion
          └─ NON → Erreur "Événement complet"

    Quand place se libère:
    ├─ Ticket marqué 'cancelled'
    ├─ Capacité +1
    ├─ TRIGGER: Promouvoir waitlist
    │  ├─ Créer nouveau ticket
    │  ├─ Mettre à jour waitlist (promoted_at=NOW)
    │  └─ Envoyer email d'invitation
    └─ Réitérer jusqu'à places pleines

╔════════════════════════════════════════════════════════════════════════════════════════════════════╗
║                                      CHECK-IN WORKFLOW                                            ║
╚════════════════════════════════════════════════════════════════════════════════════════════════════╝

    À l'entrée de l'événement:
    
    1. QR Code Scan (Mobile)
    │  └─ JSON Payload: { ticketId: "abc...", eventId: "def...", ... }
    │
    2. POST /api/module5/tickets/checkin
    │  ├─ Body: { ticketCode, ticketId, checkedInByUserId }
    │  │
    │  └─ Backend:
    │     ├─ BEGIN TX
    │     ├─ Lookup ticket (FOR UPDATE)
    │     ├─ Verify status != 'checked_in' (prevent double check-in)
    │     ├─ UPDATE status = 'checked_in'
    │     ├─ UPDATE checked_in_at = NOW()
    │     ├─ UPDATE checked_in_by_user_id = organizer_id
    │     ├─ COMMIT
    │     └─ WebSocket broadcast: "module5:ticket:checked_in"
    │
    3. UI Update
    │  └─ Green checkmark / Success message
    │
    4. Entry allowed
    │  └─ Physical access granted

║                                   CONFIGURATION & DÉPLOIEMENT                                     ║
╚════════════════════════════════════════════════════════════════════════════════════════════════════╝

    CORS Configuration:
    ├─ Allowed Origins: http://localhost:3000, http://localhost:3001
    ├─ Methods: GET, POST, PATCH, DELETE
    └─ Headers: Content-Type, Accept

    Email Configuration (Development):
    ├─ Provider: Ethereal (Test Account Auto-Created)
    ├─ No real email sent
    ├─ Preview URL returned: https://ethereal.email/message/[ID]
    └─ Perfect for testing

    Email Configuration (Production):
    ├─ Provider: Custom SMTP (Gmail, SendGrid, etc.)
    ├─ Config via ENV vars:
    │  ├─ SMTP_HOST
    │  ├─ SMTP_PORT
    │  ├─ SMTP_USER
    │  ├─ SMTP_PASS
    │  ├─ SMTP_SECURE
    │  └─ EMAIL_FROM
    └─ Real emails sent to users

    Database Transactions:
    ├─ BEGIN / COMMIT / ROLLBACK
    ├─ Isolation Level: READ COMMITTED (default)
    ├─ Row Locking: FOR UPDATE on module5.events
    └─ Prevents race conditions on capacity

    Error Handling:
    ├─ PostgreSQL 42P01 (Missing table):
    │  ├─ Endpoint /api/module2/providers → returns []
    │  └─ Graceful degradation (no crash)
    ├─ Type Coercion:
    │  ├─ price_amount: string | number
    │  └─ Automatic conversion: Number(val).toFixed(2)
    └─ CORS Issues:
       └─ Dynamic origin validation
